## 2. 四个必改文件（插件能工作的最小集）

Nav2 的插件机制要求**四处**配套，缺一不可。

### 2.1 `global_planner_plugin.xml` —— 告诉 pluginlib 去哪找类

```xml
<library path="nav2_astar_planner">
    <class type="nav2_astar_planner::AStarPlanner" base_class_type="nav2_core::GlobalPlanner">
        <description>基于 A* 算法的全局路径规划器（教学实现）</description>
    </class>
</library>
```

- `library path` = 编译出的 `.so` 名（不带 `lib` 前缀和扩展名）
- `base_class_type` 必须是 `nav2_core::GlobalPlanner`

### 2.2 `package.xml` —— 声明导出

```xml
<export>
  <build_type>ament_cmake</build_type>
  <nav2_core plugin="${prefix}/global_planner_plugin.xml"/>
</export>
```

`<nav2_core plugin=...>` 这一行会让 ament 在
`share/ament_index/resource_index/nav2_core__pluginlib__plugin/` 下生成索引，
pluginlib 才搜得倒。

### 2.3 `CMakeLists.txt` —— 两行关键

```cmake
add_library(${library_name} SHARED src/astar_planner.cpp src/astar_algorithm.cpp)
ament_target_dependencies(${library_name} ${dependencies})

# 关键 1: 导出插件描述文件
pluginlib_export_plugin_description_file(nav2_core global_planner_plugin.xml)

# 关键 2: 把 xml 也装到 share/
install(FILES global_planner_plugin.xml DESTINATION share/${PROJECT_NAME})
```

### 2.4 `src/astar_planner.cpp` 末尾 —— 导出类

```cpp
PLUGINLIB_EXPORT_CLASS(nav2_astar_planner::AStarPlanner, nav2_core::GlobalPlanner)
```

没有这一行，`.so` 里就没有注册符号，`pluginlib` 加载时会报
`Failed to load library`。

## 4. 参数配置

文件：`params/nav2_params_astar.yaml`

找到 `planner_server` 段，把 `GridBased.plugin` 换成我们的插件：

```yaml
planner_server:
  ros__parameters:
    expected_planner_frequency: 20.0
    planner_plugins: ["GridBased"]
    costmap_update_timeout: 1.0
    GridBased:
      plugin: "nav2_astar_planner::AStarPlanner"
      # ---- A* 插件参数 ----
      allow_diagonal: true            # 允许 8 邻域（含对角）
      allow_unknown: true             # 允许穿越未知区域
      cost_weight: 0.0                # 地形代价权重
      heuristic_weight: 1.0           # 1.0=最优；>1 更快但非最优
      interpolation_resolution: 0.05  # 路径插值间距(米)
      max_expansions: 1000000         # 节点扩展上限
      use_final_approach_orientation: false
```

**参数命名规则（容易踩坑）**：
参数名必须带**插件实例名**前缀，即 `GridBased.xxx`，因为
`planner_plugins: ["GridBased"]` 里定义的实例名就是 `GridBased`。
写成 `xxx` 或 `planner.xxx` 都读不到。

## 5. 启动仿真

### 5.1 启动 Gazebo + 导航栈

```bash
cd ~/ros2_jazzy/nav2_astar_ws
./run_astar_gui.sh
```

等终端出现：

```
AStarPlanner(GridBased) 已配置: allow_diagonal=1, allow_unknown=1, ...
```

说明插件已被 `planner_server` 成功加载。

### 5.2 RViz 已包含在启动中

`run_astar_gui.sh` 会同时拉起 Gazebo、导航栈和 RViz，无需单独启动。

**关键改动**：默认使用本包自带的 RViz 配置
`rviz/nav2_astar_view.rviz`，它**移除了会段错误的 Docking 面板**。
详见本文档第 8 节（RViz 段错误专题）。

若一体化启动仍遇到问题，可用备用脚本单独启动 RViz：

```bash
./run_rviz.sh
```

### 5.3 手动设置初始位姿（必须）

机器人出生在 Gazebo 的 `(-2.00, -0.50)`。在 RViz 里：

1. 点工具栏 **2D Pose Estimate**
2. 在机器人位置 `(-2.0, -0.5)` 按住左键，拖出朝向（车头朝 +x），松手
3. 观察终端出现 `AMCL ... Setting pose`

**为什么必须设**：AMCL 只有收到初始位姿才会发布 `map -> odom` 变换。
而 `global_costmap` 激活时必须能查到 `map -> base_link`，否则
`planner_server` 激活失败，整个 navigation bringup 会 abort。

### 5.4 激活导航栈

设好位姿后，导航栈可能已经因为超时而 abort（`Failed to bring up all requested nodes`）。
这时执行：

```bash
cd ~/ros2_jazzy/nav2_astar_ws
./activate_nav.sh
```

或手动激活（`ros2 lifecycle` 标准命令）：

```bash
ros2 lifecycle set /planner_server activate --no-daemon --spin-time 10
```

> **关于 `--no-daemon`**：本机 ros2cli daemon 存在 DDS 发现缓存问题，
> `ros2 node list` 会返回空。加 `--no-daemon` 可绕过。
> 若报 `Node not found`，加大 `--spin-time`（默认太短，发现来不及）。

`activate_nav.sh` 内部用 Python 单进程批量调用服务，约 3 秒完成全部激活；
而逐个用 `ros2 lifecycle set` CLI 需要 60 秒以上（每次启动 CLI 都要重做发现）。

### 5.5 验证激活状态

```bash
for n in planner_server controller_server bt_navigator; do
  printf "%-18s " "$n"
  ros2 service call /$n/get_state lifecycle_msgs/srv/GetState "{}" | grep -o "label='[a-z]*'"
done
```

期望全部 `label='active'`。

### 5.6 下发导航目标

在 RViz 里点 **Nav2 Goal**，在地图上点一个可达目标（例如 `(1.5, 0.5)`），
A* 会立刻规划并驱动机器人前往。

成功时终端会打印：

```
[planner_server]: A* 规划完成: 扩展 N 节点, 打开 M 节点, 路径 K 格, 代价 X, 耗时 Y ms
[controller_server]: Passing new path to controller.
[controller_server]: Reached the goal!
[bt_navigator]: Goal succeeded
```

## 6. 常见问题

### Q1: `Failed to load library ... libnav2_astar_planner.so`

原因依次排查：
1. 没 source `nav2_astar_ws/install/setup.bash`
2. `package.xml` 缺 `<nav2_core plugin=...>` 导出
3. `astar_planner.cpp` 末尾缺 `PLUGINLIB_EXPORT_CLASS`

### Q2: `A* 未能找到可行路径`

先确认不是地图/位姿问题（本项目实际踩过）：

```bash
# 看起点终点代价
ros2 topic echo /global_costmap/costmap_raw --once | head
```

常见原因：
- **初始位姿设错**（最常发生）：比如机器人实际在 `(-2.0,-0.5)`，你设成了 `(0,0)`，
  AMCL 认为机器人在墙里，规划自然无解
- 目标点在障碍上或不可达
- `allow_unknown: false` 但地图未知区很大

### Q3: `terminate called without an active exception` + `class_loader` 警告

发生在**关闭**阶段：rcl context 已失效时 `class_loader` 尝试卸载库。
无头模式不出现，GUI + `use_composition:=False` 下偶发。
**不影响导航功能**，是 nav2 关闭序列的已知现象（官方 `controller_server` 也会中招）。

### Q4: `ros2 lifecycle` 报 `invalid choice: 'lifecycle'`

说明 `ros2lifecycle` 包没构建成功。本机遇到的情况是：该包历史上被
`SIGINT` 中断过（`build/ros2lifecycle/colcon_build.rc` 内容为 `SIGINT`），
导致 `install/` 下只有 hook 没有 Python 包。修复：

```bash
cd ~/ros2_jazzy
rm -rf build/ros2lifecycle install/ros2lifecycle
colcon build --base-paths src/ros2 --packages-select ros2lifecycle
```

同样的问题也影响 `ros2 component`，可一并修复：
```bash
rm -rf build/ros2component install/ros2component
colcon build --base-paths src/ros2 --packages-select ros2component
```

### Q5: Gazebo 报 `Unable to find or download file`

这是 nav2 官方 launch 的竞态 bug，本仓库已修复（见
`~/ros2_jazzy/NAV2_SIM_README.md`）。若重新克隆源码需重新打补丁：
`git apply ~/ros2_jazzy/fix-gazebo-xacro-race.patch`

## 8. 专题：RViz Docking 面板段错误（exit -11）

### 8.1 现象

用官方默认 RViz 配置（`nav2_default_view.rviz`）启动时，RViz 必定崩溃：

```
[nav2_rviz_selector_node]: Trying to load plugins...
[nav2_rviz_docking_panel_node]: Loading dock plugins        ← 最后一行
[ERROR] [rviz2-6]: process has died [exit code -11]         ← 立刻 SIGSEGV
```

而 RViz 崩溃后，同一 launch 里的 Gazebo、lifecycle_manager 会跟着一起死。

实测崩溃率：**4/4 次（约 100%）**，历时约 50 秒后触发。

### 8.2 根因（已定位到源码行）

这是 **nav2 官方已知 bug**，见
[navigation2 issue #4689](https://github.com/ros-navigation/navigation2/issues/4689)。

官方给出的崩溃栈关键帧：

```
#0 rclcpp::ParameterValue::get<9> (this=0x20)              ← 空指针
#1 rclcpp::Parameter::get_value<9> (this=0x0)
#2 rclcpp::Parameter::as_string_array() (this=0x0)         ← 解引用空指针
#3 nav2_rviz_plugins::pluginLoader(...)
#4 nav2_rviz_plugins::DockingPanel::timerEvent(...)
```

对应本机源码 `nav2_rviz_plugins/src/utils.cpp:53`：

```cpp
auto parameters = parameter_client->get_parameters({plugin_type});
auto str_arr = parameters[0].as_string_array();   // ← parameters 为空时越界
```

**触发条件：时序竞态**。本机实测的时间线：

| 时刻 | 事件 |
|---|---|
| `...151.116` | `docking_server: Creating`（节点刚创建，**尚未 configure**） |
| `...151.917` | RViz `Loading dock plugins` → **段错误** |
| `...155.054` | `docking_server: Configuring`（**4 秒后才 configure**） |

RViz 在 `docking_server` 还没 configure 完成时就发起参数查询，
`get_parameters` 返回**空数组**，`parameters[0]` 越界，
`as_string_array()` 在空指针上调用 → SIGSEGV。

这解释了为什么它是"随机"崩溃：取决于 RViz 和 docking_server 谁先就绪。
CPU 负载高时更容易触发（官方 issue 里用 `stress` 复现）。

### 8.3 三种解决方案（按推荐度排序）

#### 方案 A：移除 Docking 面板（推荐，本项目采用）

**做法**：从 RViz 配置里删掉这两行

```yaml
  - Class: nav2_rviz_plugins/Docking
    Name: Docking
```

**本项目已实现**：`rviz/nav2_astar_view.rviz`（从官方配置移除该面板，
保留 `Navigation 2` 和 `Selector`）。launch 默认加载它。

**实测效果**：3/3 次 + 2/2 次全部稳定，`Loading dock plugins` 出现 0 次。

**代价**：失去 RViz 里的对接（docking）操作面板。本教程用不到该功能，
导航（Nav2 Goal）完全不受影响。

#### 方案 B：禁用组合模式

官方 issue 中报告者明确说明：

> "The crash doesn't seem to happen if I disable `use_composition`."

即加 `use_composition:=False`。

**注意**：本项目实测——**单独用 B 不够**。在
`use_composition:=False` 下崩溃依然 4/4 复现。所以 B 必须配合 A 使用，
或至少不能替代 A。（这与本机 nav2 版本 1.3.14、WSLg 环境的特定时序有关。）

#### 方案 C：延迟启动 RViz

等导航栈完全激活后再起 RViz，让 `docking_server` 先就绪。
等效于分离启动（本项目 `run_rviz.sh` 的做法）。
稳定性好，但需要手动分两步。

### 8.4 上游修复状态

该 bug 已由 nav2 PR [#4717](https://github.com/ros-navigation/navigation2/pull/4717)
修复（作者 ajtudela），修复形式是把 `timerEvent` 里反复调用的
`pluginLoader` 改为**状态机 + 只加载一次**：

```cpp
// 本机 1.3.14 的 docking_panel.cpp（已含此改造）
QObject::connect(initial_thread_, &InitialDockThread::dockingActive, [this] {
    if (!plugins_loaded_) {                      // ← 只加载一次
      nav2_rviz_plugins::pluginLoader(...);
      plugins_loaded_ = true;
    }
  });
```

**但**本机 1.3.14 的 `utils.cpp:53` 仍然**没有空数组检查**：

```cpp
auto str_arr = parameters[0].as_string_array();   // 仍是隐患
```

所以即使 1.3.14 已包含 #4717 的主体改造，本机仍 100% 崩溃。
彻底的修复需要在上游补上 `parameters.empty()` 判断。

### 8.5 补充：与 WSL 环境无关

排查过程中确认，本案的崩溃**不是 WSLg/OpenGL 问题**：

- 本机 WSL 内核 `6.18.58.1`、WSLg `1.0.79`，均已较新
- RViz **单独启动**（`run_rviz.sh`）能正常运行，说明 OpenGL 渲染正常
- 崩溃精确发生在 `Loading dock plugins` 之后，是应用层空指针，非图形栈问题

> 另有一条 WSL 下 RViz 段的 issue
> [ros2/rviz#1218](https://github.com/ros2/rviz/issues/1218)，
> 报告者用 `wsl --update` 解决。但那是"启动即崩"、用 VcXsrv 的场景，
> **与本项目症状不同**，不适用。

### 8.6 如果你想用回官方配置

若你确实需要 Docking 面板，可以手动改回并在崩溃后重试：

```bash
# 用官方配置启动（会崩，但可以在崩前操作，或反复重试）
./run_astar_gui.sh   # 然后手动替换 rviz 配置路径
```

更稳妥的做法是等上游补上空数组检查后再启用。
