## 阶段 2-3：算法与插件实现

### 设计决策

**把算法与 ROS 解耦**：
- `astar_algorithm.{hpp,cpp}` —— 纯 C++，不 include 任何 ROS 头文件
- `astar_planner.{hpp,cpp}` —— 负责 ROS 交互，把 costmap 转成 `vector<uint8_t>` 喂给算法

好处：算法可以脱离 ROS 单独测试（后面正是靠这一点定位了 bug）。

### 第一次编译失败：3 个错误

```
error: 'traversability_checker_' was not declared in this scope
error: no declaration matches 'plan(..., std::function<bool()>)'
      candidate is: 'plan(..., int)'
error: nav2_msgs/msg/path.hpp: No such file or directory
```

**根因 1**：`astar_algorithm.hpp` 漏了 `#include <functional>`。
缺它导致 `std::function` 无法解析，编译器把它当成 `int`，
于是后面所有依赖它的成员声明全部失效 —— 报错的"int"就是这么来的。

**根因 2**：`Path` 消息在 `nav_msgs`，不是 `nav2_msgs`。
`nav2_msgs` 里只有 action（如 `ComputePathToPose`）和自定义消息，没有 `Path`。

**修复**：
```cpp
#include <functional>              // 补上
#include "nav_msgs/msg/path.hpp"   // nav2_msgs → nav_msgs
```
同时把 `nav_msgs` 加进 `CMakeLists.txt` 的依赖列表。

> **教训**：一个看似无关的编译错误（`candidate is: plan(..., int)`），
> 根因可能只是一个缺失的 `#include`。编译器的类型推断会"猜"错类型，
> 报错信息会把你带偏。遇到"某某被解析成 int"，先查 include。

## 阶段 6：端到端验证（最曲折的部分）

### 6.1 插件加载成功 —— 第一个里程碑

```
[planner_server]: Created global planner plugin GridBased of type nav2_astar_planner::AStarPlanner
[planner_server]: AStarPlanner(GridBased) 已配置: allow_diagonal=1, allow_unknown=1, ...
```

说明 pluginlib 四件套全部正确。

### 6.2 坑一：`XMLPARSER Error: realpath failed`

**现象**：满屏 `[XMLPARSER Error] realpath failed No such file or directory`，
伴随 DDS 通信异常、服务无响应。

**根因**：我之前调试时设过
`export FASTRTPS_DEFAULT_PROFILES_FILE=~/ros2_jazzy/fastdds_tuned.xml`，
后来**清理调试残留时把该文件删了，但环境变量还留在 shell 里**，
指向一个不存在的路径。Fast DDS 每次启动都尝试解析这个空路径，于是报错。

**修复**：`unset FASTRTPS_DEFAULT_PROFILES_FILE`

> **教训 1**：不要为了排查问题而随便改全局环境变量。这类改动会
> 在后续所有进程里生效，一旦忘记清理就会制造更难查的新故障。
>
> **教训 2**：清理调试文件时要同步清理引用它的环境变量。
>
> **教训 3**：这个错误我一开始误判成"DDS 传输层问题"，
> 在上面浪费了好几轮。实际是一行环境变量的问题 —— 看到
> "realpath failed"，先查环境变量里有没有指向不存在文件的路径。

### 6.3 坑二：`/tf_static` 收不到数据

**现象**：`/joint_states` 有 108 帧，但 `/tf_static` 完全为空，
导致 `base_link` 不存在，`controller_server` 激活失败。

**排查过程**（有弯路）：
1. 先怀疑 QoS —— `/tf_static` 是 `transient_local`，我的探测节点默认
   QoS 不对。**这个怀疑是对的**，但改对 QoS 后依然为空。
2. 怀疑 DDS 传输。
3. 最终发现：**有两个 `robot_state_publisher` 进程在跑**
   （PID 52980 和 55287），来自不同的 launch 实例，互相冲突。

**根因**：反复启动/中断留下的残留进程。`pkill -f tb3_simulation` 只能
杀掉 launch 父进程，**杀不掉它 fork 出来的独立节点进程**（因为
`use_composition:=False` 时每个 nav2 节点都是独立进程）。

**修复**：逐个 pattern 彻底清理：

```bash
for pat in "nav2_controller" "nav2_bt_navigator" "nav2_planner" "nav2_amcl" \
           "nav2_map_server" "nav2_smoother" "nav2_behaviors" \
           "nav2_velocity_smoother" "nav2_collision_monitor" \
           "nav2_waypoint_follower" "opennav_docking" "nav2_route" \
           "nav2_lifecycle_manager" "gz sim" "rviz2" "parameter_bridge" \
           "robot_state_publisher" "ros2launch"; do
  pkill -9 -f "$pat"
done
rm -f /dev/shm/fastrtps_*
```

> **教训**：`use_composition:=False` 时，`pkill` launch 名称是不够的。
> 启动新实例前**必须**确认进程树干净，否则会遇到各种"诡异"现象
> （TF 为空、进程重复、日志消失），全都是残留进程在干扰。

### 6.4 坑三：A* 报"无可行路径"——本项目最有价值的 bug

**现象**：
```
[planner_server]: GridBased plugin failed to plan from (-0.05, 0.00) to (1.50, 0.50):
"A* 未能找到可行路径"
```

**排查过程**：这是最关键的一段，值得详细记录。

**Step 1**：加诊断日志，打印实际数据。
```cpp
RCLCPP_WARN(logger_, "[DEBUG] map=%ux%u start=(%d,%d) goal=(%d,%d) start_cost=%u goal_cost=%u",
            size_x, size_y, start_grid.x, start_grid.y, goal_grid.x, goal_grid.y,
            costs[...], costs[...]);
```
输出：
```
start_cost=253  goal_cost=173  allow_unknown=1 allow_diagonal=1
```

**Step 2**：发现 `start_cost=253`，而我的阈值是 `< 253` → 起点不可通行。

但改阈值前，先**验证算法本身是否正确**。做法：把算法逻辑用 Python
照着写一遍，喂同样的数据：

```python
# 用 cost<254 判定，起点(199,200) 终点(229,209)
Python A*: 找到=False 扩展=7
```

结果一致（找不到）。说明 **C++ 实现没问题**，问题在数据或阈值。

**Step 3**：打印起点周围 11×11 的代价分布 —— 一眼看清。

```
  I  I  I  I  I  I  I  I  I  I  I
  I  I  I  I  F  F  F  F  I  I  I
  I  I  I  I  F  F  F  F  F  I  I
  I  I  I  F  F  I  I  F  F  F  I
  I  I  I  F  F  I  I  I  F  F  I    ← I=253(内切膨胀) F=254(致命障碍)
  I  I  I  F  F  I  I  I  F  F  I    ← 机器人被 F 围在一个封闭区域里
  I  I  I  I  F  F  F  F  F  I  I
  I  I  I  I  I  F  F  F  I  I  I
  I  I  I  I  I  I  I  I  I  I  I
```

**Step 4**：确认这是"真·无路可走"，去查为什么机器人在墙里。

**真正的根因**：**初始位姿设错了**。

- Gazebo 里机器人出生点：`(-2.00, -0.50)`（见 `spawn_tb3.launch.py` 默认值）
- 我给 AMCL 的初始位姿：`(0.0, 0.0)` ❌
- 后果：AMCL 认为机器人在 `(0,0)`，而地图上 `(0,0)` 恰好是障碍区，
  于是 `map→odom` 变换错位，代价地图上机器人被"传送"到墙里，
  规划自然无解。

**修复**：初始位姿改为 `(-2.0, -0.5)`。

**验证**：改完立刻成功：
```
[controller_server]: Reached the goal!
[bt_navigator]: Goal succeeded
```

> **核心教训**：报"无可行路径"时，**第一件事是确认起点和终点在代价地图上
> 的坐标和代价**，而不是怀疑算法。
>
> 更重要的：**初始位姿必须与 Gazebo 出生点一致**。这是 ROS 导航里
> 非常经典的坑 —— 位姿错了，TF 就错，代价地图就错，一切下游判断都错，
> 但报错信息只会说"找不到路径"，完全指不到真实原因。

### 6.5 坑四：RViz 段错误拖垮整个 launch

**现象**：`headless:=False use_rviz:=True` 时：
```
[rviz2-6]: process has died [pid 127462, exit code -11]   ← SIGSEGV
[planner_server-12]: process has died [pid 127469, exit code -6]  ← SIGABRT
[gz-21]: process has died [pid 127595, exit code -9]
```

整栈崩溃。

**排查**：
1. 先测 `headless:=False use_rviz:=False` → Gazebo 和 GUI 都 ALIVE ✓
2. 再单独 `ros2 run rviz2 rviz2 -d nav2_default_view.rviz` → RViz 也能 ALIVE ✓

结论：**RViz 单独能跑，但和导航栈在同一个 launch 里就崩**。
问题出在 `nav2_rviz_plugins` 的 docking 面板在 WSLg 下段错误，
launch 检测到子进程崩溃后会级联关闭其他进程。

**当时先用分离启动规避**：
```bash
./run_astar_gui.sh   # 终端 1：Gazebo + 导航栈（use_rviz:=False）
./run_rviz.sh        # 终端 2：RViz 单独跑
```

**后续已彻底解决**（见下文"阶段 8"）：移除了 RViz 配置里会崩溃的
Docking 面板，现在可以一体化启动。

> **教训**：`use_composition:=False` 让每个节点独立进程，好处是
> 故障隔离（一个崩不影响别的），但 launch 的"级联关闭"机制仍会
> 因为任一进程崩溃而拉垮全局。分离启动是最稳的调试方式。

### 6.6 坑五：`terminate called without an active exception`

**现象**：关闭时 `planner_server` / `controller_server` 以 `exit -6` 崩溃：
```
[ERROR] [global_costmap]: Original error: could not create subscription:
        rcl node's context is invalid
Warning: class_loader.ClassLoader: SEVERE WARNING!!! Attempting to unload
         library while objects created by this loader exist in the heap!
terminate called without an active exception
```

**分析**：
- 发生在 **shutdown 阶段**，此时 rcl context 已失效
- `class_loader` 尝试卸载插件库，但插件对象还在堆上 → 警告
- 随后 `terminate` → abort

**关键证据**：这个问题在 **官方 `controller_server`（DWB 控制器，
完全是官方代码）上同样出现**，说明**不是我插件的问题**，而是
nav2 在本环境下的关闭序列问题。

**结论**：**不影响导航功能**，只在退出时出现。可忽略。

> **教训**：判断"是不是我代码的 bug"时，最好的方法是看**官方组件
> 是否也有同样现象**。如果官方组件也崩，那就是环境/框架问题。

## 阶段 8：RViz 段错误的彻底解决（联网查证 + 实测）

### 8.1 为什么要查

阶段 6.5 只是"绕开"了 RViz 段错误（分离启动），没有解决根因。
用户要求查证网络上是否有解决方案，于是做了完整的联网排查。

### 8.2 查到三条相关 issue

| Issue | 相关性 |
|---|---|
| [navigation2#4689](https://github.com/ros-navigation/navigation2/issues/4689) | **高度相关**，正是 DockingPanel 崩溃，且有完整崩溃栈 |
| [ros2/rviz#1218](https://github.com/ros2/rviz/issues/1218) | 不适用，是 WSL 下"启动即崩"+VcXsrv 场景 |
| [ros2/rviz#935](https://github.com/ros2/rviz/issues/935) | 参考价值低，是另一个 costmap 相关崩溃 |

### 8.3 定位到源码行

issue #4689 给出的崩溃栈关键帧：

```
#2 rclcpp::Parameter::as_string_array[abi:cxx11]() const (this=0x0)   ← 空指针
#3 nav2_rviz_plugins::pluginLoader(...)
#4 nav2_rviz_plugins::DockingPanel::timerEvent(...)
```

对应本机 `nav2_rviz_plugins/src/utils.cpp:53`：

```cpp
auto parameters = parameter_client->get_parameters({plugin_type});
auto str_arr = parameters[0].as_string_array();   // 空数组时越界
```

### 8.4 实测确认时序竞态

本机时间线：

| 时刻（同一次启动） | 事件 |
|---|---|
| `151.116` | `docking_server: Creating`（尚未 configure） |
| `151.917` | RViz `Loading dock plugins` → **SIGSEGV** |
| `155.054` | `docking_server: Configuring`（晚 4 秒） |

**结论**：RViz 在 docking_server 未就绪时查参数 → 拿到空数组 → `parameters[0]` 越界 → 空指针解引用。

### 8.5 方案验证（用数据说话）

| 方案 | 实测结果 |
|---|---|
| 基线（官方 rviz 配置） | **4/4 崩溃**，约 50 秒触发 |
| `use_composition:=False` 单用 | **仍 4/4 崩溃** ← 关键发现，单靠它不够 |
| 移除 Docking 面板 | **3/3 + 2/2 全部稳定**，`Loading dock plugins` 出现 0 次 |

> 注意与官方 issue 的差异：官方报告者说 `use_composition:=False` 可避免崩溃，
> 但**本机实测不行**。可能是 nav2 版本（1.3.14）或 WSLg 时序差异。
> 所以最终方案选的是"移除面板"，它直接消除了崩溃触发点，最可靠。

### 8.6 上游修复状态

### 8.9 教训

1. **"绕开"不等于"解决"**。分离启动能用，但掩盖了真实问题。查证后

## 阶段 9：修复 `ros2 lifecycle` 缺失（用户指出）

### 9.1 我之前的错误做法

我在文档里写"本机 `ros2 lifecycle` 不可用，用 `change_state` 服务代替"，
并把它当成环境事实接受下来。用户直接指出：**"你就安装不就好了"**。

这是对的。我把一个"可修复的缺失"当成了"环境的限制"，属于
**把绕开方案当结论**——和之前 RViz 段错误的问题同一种思维惰性。

### 9.2 真实原因

排查发现三个事实：

```bash
# 1. /opt 里确实没有
ls /opt/ros/jazzy/share/ros2lifecycle          → 不存在

# 2. 但工作空间里有目录，却只有 hook 没有 Python 包
ls install/ros2lifecycle                       → 只有 share/ros2lifecycle/hook

# 3. 构建返回码是 SIGINT
cat build/ros2lifecycle/colcon_build.rc        → SIGINT
```

**根因**：这个包在历史某次 `colcon build` 中被中断（SIGINT），
留下一个只有 hook 的残缺 install 目录。之后因为目录存在，
构建系统没再重试它，`ros2cli` 也就一直找不到 `ros2lifecycle` 扩展。

而 `ros2topic` 能用的原因是它的 Python 包在 `build/ros2topic/ros2topic/`
里（通过 `PYTHONPATH` 生效），`ros2lifecycle` 的 `build/` 里什么都没有。

### 9.3 修复

```bash
cd ~/ros2_jazzy
rm -rf build/ros2lifecycle install/ros2lifecycle
colcon build --base-paths src/ros2 --packages-select ros2lifecycle
```

39 秒完成。验证：

```bash
$ ros2 lifecycle --help
Commands:
  get    Get lifecycle state for one or more nodes
  list   Output a list of available transitions
  nodes  Output a list of nodes with lifecycle
  set    Trigger lifecycle state transition
```

四个子命令齐全，**命令可用**。

### 9.4 顺带发现：24 个包同样是 SIGINT 残缺状态

```bash
for d in build/*/; do
  rc=$(head -1 "$d/colcon_build.rc" 2>/dev/null)
  [ "$rc" != "0" ] && echo "$(basename $d): $rc"
done
```

结果 24 个，包括 `ros2component`、`ros2param`、`sros2`、`lifecycle_py`、
`rosbag2_transport` 等。其中 `ros2 component` 实测确实不可用，已一并修复：

```bash
rm -rf build/ros2component install/ros2component
colcon build --base-paths src/ros2 --packages-select ros2component
```

> 这些残缺大概率是我在之前多轮排查 nav2 时，
> 反复 `pkill` 恰好打到了正在进行的 `colcon build` 上造成的。

### 9.5 发现 daemon 缓存问题（新坑）

`ros2 lifecycle` 装好后，`get` 仍报 `Node not found`。排查发现：

```bash
$ ros2 node list                    → 0 个节点  ✗
$ ros2 node list --no-daemon        → 正常列出  ✓
```

**结论**：本机 ros2cli **daemon 的 DDS 发现缓存有问题**，不是 lifecycle 的问题。
以后所有 ros2 CLI 查询统一加 `--no-daemon`。

另外 `--spin-time` 默认值太短，DDS 发现来不及完成就超时，
需要显式加 `--spin-time 10`。

### 9.6 `ros2 lifecycle get` 的参数限制

实测发现它**只接受一个节点名**：

```bash
ros2 lifecycle get /planner_server /controller_server   → error: unrecognized arguments
```

不带参数则列出全部节点状态（这个最实用）：

```bash
$ ros2 lifecycle get --no-daemon --spin-time 5
/amcl: active [3]
/behavior_server: inactive [2]
/bt_navigator: active [3]
...
```

### 9.7 性能问题：CLI 逐个查询太慢

实测单次 `ros2 lifecycle get` 耗时 **6.9 秒**（每次启动新 CLI 进程都要
重做一遍 DDS 发现）。8 个节点 = 55 秒以上，导致 `activate_nav.sh` 运行超时。

**解决方案**：改用 Python 单进程，复用同一个 rclpy 节点批量调用服务：

```python
for n in NODES:
    call(node, GetState, f'/{n}/get_state', GetState.Request(), timeout=3.0)
```

**实测效果**：

| 方式 | 10 个节点耗时 |
|---|---|
| `ros2 lifecycle get` CLI 逐个 | ~69 秒 |
| Python 单进程批量 | **3.6 秒**（快约 20 倍） |

激活全部节点 + 查询：**2.85 秒**。

已固化为 `src/nav2_astar_planner/activate_nodes.py`，
`activate_nav.sh` 直接调用它。

### 9.8 教训（第二次同类错误）

1. **环境缺失 ≠ 环境限制**。先查"为什么缺"（返回码、日志、安装内容），
   而不是直接写"不可用"然后绕开。`colcon_build.rc` 里的 `SIGINT`
   一眼就能定位，我却没查。
2. **我的 `pkill` 在污染构建**。反复 `pkill -9` 打断 `colcon build`，
   制造了 24 个残缺包。以后批量 kill 要注意别打到构建进程。
3. **CLI 慢就该换 API**。6.9 秒/次这种数量级，说明工具选错了，
   应该直接用 rclpy 而不是硬等。

### 10.2 环境持久化到 `.bashrc`

**问题**：之前每次开新终端都要手动 source 三个 setup 文件，且有多个
易忘的环境要求（`GZ_SIM_RESOURCE_PATH`、要 unset 的 DDS 变量）。

**做法**：备份 `.bashrc` 后追加带标记的配置块（便于以后定位/删除）：

```bash
cp ~/.bashrc ~/.bashrc.bak.$(date +%Y%m%d_%H%M%S)
```

写入内容（用 `ROS2_ASTAR_SETUP_BEGIN/END` 包裹）：

```bash
# >>> ROS2_ASTAR_SETUP_BEGIN >>>
# 三级 source（顺序不能错）
source /opt/ros/jazzy/setup.bash
[ -f "$HOME/ros2_jazzy/install/setup.bash" ] && source "$HOME/ros2_jazzy/install/setup.bash"
[ -f "$HOME/ros2_jazzy/nav2_astar_ws/install/setup.bash" ] && source "$HOME/ros2_jazzy/nav2_astar_ws/install/setup.bash"

# Gazebo 资源路径（model:// 和 package:// 都靠它解析）
export GZ_SIM_RESOURCE_PATH="/opt/ros/jazzy/share/nav2_minimal_tb3_sim/models:/opt/ros/jazzy/share${GZ_SIM_RESOURCE_PATH:+:$GZ_SIM_RESOURCE_PATH}"

# 自愈：若 FASTRTPS 变量指向不存在的文件则清除（否则满屏 XMLPARSER 报错）
if [ -n "$FASTRTPS_DEFAULT_PROFILES_FILE" ] && [ ! -f "$FASTRTPS_DEFAULT_PROFILES_FILE" ]; then
    unset FASTRTPS_DEFAULT_PROFILES_FILE
fi
# <<< ROS2_ASTAR_SETUP_END <<<
```

**设计要点**：

1. **三级 source 顺序正确**：`/opt` → 外层工作空间 → A* 工作空间。
   顺序反了会导致 `ros2launch`、`nav2_core` 等找不到。
2. **用 `[ -f ]` 判断存在**，避免某个工作空间被删后整个 `.bashrc` 报错。
3. **DDS 变量自愈**：这是我们在阶段 6.2 踩的坑——删了配置文件却没清
   环境变量，导致满屏 `XMLPARSER Error: realpath failed`。现在自动检测。
4. **带标记注释**，以后想撤销只需删掉两个标记之间的内容。

**验证（新登录 shell 自动生效）**：

```bash

OK
```
