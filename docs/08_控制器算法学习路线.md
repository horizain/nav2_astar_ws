## 0. 三个直接回答

### 0.1 Nav2 里最简单的 controller 是什么？

分两种说法：

| 说法 | 答案 |
|---|---|
| **官方现成、最容易用** | `nav2_regulated_pure_pursuit_controller::RegulatedPurePursuitController`（RPP） |
| **自己从零实现、最容易懂** | **Pure Pursuit（纯跟踪）**，RPP 就是它的工程化版本 |
| **最容易误解的“简单”** | PID。PID 是控制分量，不是完整的路径跟踪器 |

Pure Pursuit 的核心只有三步：

1. 在全局路径上找一个“前视点”（lookahead point）；
2. 把前视点变换到机器人坐标系；
3. 用几何关系算曲率，再转成角速度。

它没有采样、没有优化、没有 critics，代码量可以控制在 100 行左右，
而且天然考虑差速机器人的非完整约束（不能横着走）。

### 0.2 局部路径规划器有吗？

有。Nav2 里它叫 **controller**，不叫 local planner。

```text
planner_server      → 全局路径（A*）
controller_server   → 局部轨迹 / 速度指令（Pure Pursuit、DWB、MPPI、MPC...）
```

DWB、MPPI、MPC 内部确实会“规划”未来一小段轨迹，所以它们既是局部规划器，
也是控制器。Pure Pursuit / Stanley 更偏“几何跟踪”，不显式采样未来轨迹。

### 0.3 为什么不直接用 PID 跟踪路径？

**可以，但“PID 跟踪路径”这句话省略了太多关键设计。**

PID 是一个**反馈律**，它需要你告诉它：

- 跟踪哪个量？横向误差？航向误差？还是 x、y 两个方向的位置误差？
- 参考点在哪？路径上最近点？前方 lookahead 点？按时间采样的轨迹点？
- 输出怎么映射到差速机器人？PID 输出的是“力/速度”，但机器人只能控制 `v` 和 `ω`；
- 遇到弯道、障碍、速度限制、倒车怎么办？

所以：

- **PID 可以作为控制器内部的一个分量**：速度 PID、横向误差 PID、舵角 PID；
- **PID 本身不是完整的路径跟踪算法**；
- 对差速机器人，直接对 `(x, y)` 做两个 PID，会试图让机器人“横着走”，
  与差速约束冲突；
- 对路径跟踪，更自然的是 Pure Pursuit / Stanley 这类几何方法，
  或者 DWB / MPPI / MPC 这类“预测未来并评估代价”的方法。

第 5 节会详细对比。

## 1. 推荐的学习阶梯

不要一上来写 MPPI。按这个顺序，每一级只增加一个概念：

| 级别 | 控制器 | 类型 | 难度 | 对应 Nav2 官方 | 你会学到 |
|---|---|---|---|---|---|
| L0 | **PID 基线** | 反馈控制 | ★ | 无（不是完整控制器） | 为什么 PID 单独不够 |
| L1 | **Pure Pursuit** | 几何跟踪 | ★ | `RegulatedPurePursuitController` | lookahead、曲率、非完整约束 |
| L2 | **Stanley** | 几何 + 横向误差 | ★★ | 无完全对应 | 前轴、横向误差、航向误差 |
| L3 | **DWB-lite** | 采样 + critics | ★★★ | `DWBLocalPlanner` | 轨迹 rollout、代价评分、局部避障 |
| L4 | **MPPI-lite** | 采样 + 软最大 | ★★★★ | `MPPIController` | 随机采样、温度、序列优化 |
| L5 | **MPC-lite** | 梯度优化 | ★★★★ | 无（Nav2 核心外） | 控制序列优化、约束投影、线搜索 |
| L6（选做） | 完整 MPC/QP | 优化 | ★★★★★ | 无 | QP/NLP 求解器、硬约束 |

> **建议先做 L0 + L1**。L0 用来回答“PID 行不行”，L1 用来建立
> “路径跟踪”的正确直觉。L2 是补充，L3/L4/L5 才是局部规划器。

## 3. 先搞懂 Nav2 Controller 契约

`nav2_core::Controller` 的纯虚函数（Jazzy）：

```cpp
class Controller
{
public:
  virtual void configure(
    const rclcpp_lifecycle::LifecycleNode::WeakPtr & parent,
    std::string name,
    std::shared_ptr<tf2_ros::Buffer> tf,
    std::shared_ptr<nav2_costmap_2d::Costmap2DROS> costmap_ros) = 0;

  virtual void cleanup() = 0;
  virtual void activate() = 0;
  virtual void deactivate() = 0;

  virtual void setPlan(const nav_msgs::msg::Path & path) = 0;

  virtual geometry_msgs::msg::TwistStamped computeVelocityCommands(
    const geometry_msgs::msg::PoseStamped & pose,
    const geometry_msgs::msg::Twist & velocity,
    nav2_core::GoalChecker * goal_checker) = 0;

  virtual void setSpeedLimit(const double & speed_limit, const bool & percentage) = 0;
};
```

你需要记住的几件事：

| 事项 | 说明 |
|---|---|
| `setPlan` | 全局路径更新时调用；保存路径，可能要做坐标变换 |
| `computeVelocityCommands` | 每个控制周期调用（本项目 20 Hz），返回 `v` 和 `ω` |
| `pose` | 机器人当前位姿，在**局部代价地图的全局坐标系**下（通常是 `odom`） |
| `path` | 来自全局规划器，`header.frame_id` 通常是 `map` |
| `costmap_ros` | 局部代价地图（`local_costmap`），不是全局地图 |
| `goal_checker` | 官方目标检查器；通常直接用它的 `isGoalReached` |
| `setSpeedLimit` | 速度限制回调，内部要保存并 clamp |

**坐标系是第一个坑**：

- 全局路径在 `map`；
- 控制器位姿和局部代价地图在 `odom`；
- 必须用 `tf2_ros::Buffer` 把路径变换到局部代价地图坐标系，或者把位姿变换到 `map`。
- 不要假设两者相同。

官方控制器一般会：

1. `setPlan` 时保存路径；
2. 每次 `computeVelocityCommands` 前，用 TF 把路径变换到局部代价地图坐标系；
3. 或者只保留路径中机器人附近的一段（`transformGlobalPlan` / pruning）。

教学实现可以先做“整条路径变换到 odom”，简单但可行。

## 4. 六个算法逐个讲

### 4.1 L0：PID 基线（用来回答“为什么不用 PID”）

我们不是要写一个“PID 控制器插件”去和 MPPI 比，
而是写一个**最小闭环**，让你亲眼看到它的问题。

#### 最小思路

1. 在路径上找离机器人最近的点作为参考点；
2. 算横向误差 `e_y`（机器人到路径的垂直距离）；
3. 算航向误差 `e_θ = normalize(path_yaw - robot_yaw)`；
4. 用两个 PID/PD 分别控制角速度和线速度：

```text
# e_y 以“机器人在路径左侧为正”
ω = kp_θ · e_θ + kd_θ · d(e_θ)/dt - kp_y · e_y
v = v_des · (1 - k_v · min(1, |e_θ| / θ_max))
```

#### 你会观察到的现象

| 场景 | PID 表现 |
|---|---|
| 直线 | 还行 |
| 圆弧 | 有稳态横向误差，需要积分项 |
| 急转弯 | 反应滞后，容易切角或过冲 |
| 高速度 | 振荡，需要重新调参 |
| 有障碍 | 完全不管，直接撞 |
| 倒车 | 需要单独的符号/逻辑 |

#### 结论

PID 可以作为“速度环”或“舵角环”，但**不能单独承担局部规划**。
把它作为 L0，是为了后面比较“几何法”和“采样法”到底多了什么。

---

### 4.2 L1：Pure Pursuit（纯跟踪，最推荐先写）

#### 核心思想

不要盯着脚下的路径，盯着前方一个点。

```text
                     ● 前视点 P（路径上，距离 L）
                    /
                   /
                  /  L
                 /
                ● 机器人
```

#### 算法步骤

1. 找到路径上离机器人最近的点 `C`；
2. 从 `C` 沿路径往前走，找到距离机器人约 `L` 的点 `P`；
3. 把 `P` 变换到机器人坐标系：

```text
dx = P.x - robot.x
dy = P.y - robot.y
local_x =  cos(yaw) * dx + sin(yaw) * dy
local_y = -sin(yaw) * dx + cos(yaw) * dy
```

4. 计算曲率：

```text
κ = 2 · local_y / (local_x² + local_y²)
```

5. 转成角速度：

```text
ω = v · κ
```

6. 线速度可以用固定值，也可以按曲率/障碍/目标距离调节。

#### 关键参数

| 参数 | 作用 | 典型值 |
|---|---|---|
| `lookahead_distance` | 前视距离 | 0.5~1.0 m |
| `min_lookahead` | 最小前视距离 | 0.3 m |
| `max_lookahead` | 最大前视距离 | 1.5 m |
| `lookahead_time` | `L = v · t` 的自适应系数 | 1.0 s |
| `max_linear_vel` | 线速度上限 | 0.5 m/s |
| `max_angular_vel` | 角速度上限 | 1.9 rad/s |

#### 常见坑

| 现象 | 原因 | 调整 |
|---|---|---|
| 左右摆动 | `L` 太小 | 增大 `L` |
| 切内弯 | `L` 太大 | 减小 `L` |
| 到终点不减速 | 没有终点处理 | 距离目标 < tolerance 时减速/停止 |
| 前视点在身后 | 路径起点附近/倒车 | 特殊处理：原地转或缩小 `L` |
| 路径点太稀 | 全局路径没插值 | 先插值/重采样 |

#### 为什么它比 PID 更适合入门

- 一个参数 `L` 就能跑；
- 几何关系直接给出 `ω`，天然满足差速约束；
- 能直观看到“前视距离”对稳定性和切角的影响；
- 是官方 RPP 的基础，学完能直接读 RPP 源码。

### 4.3 L2：Stanley（横向误差 + 航向误差）

#### 核心思想

Pure Pursuit 看前方一个点；Stanley 看**前轴**到路径的横向误差，
同时修正航向。

```text
# e 以“机器人在路径左侧为正”
δ = k_heading · ψ_e - atan(k_cross · e / (v + ε))
```

- `ψ_e`：航向误差（路径切线方向 - 车头方向）；
- `e`：前轴到路径的横向误差；
- `k`：横向误差增益；
- `v`：线速度（速度越低，转向越激进，所以分母有 `v`）。

对差速机器人，可以把“舵角”换算成角速度：

```text
ω = v · tan(δ) / wheelbase
```

或者直接用比例形式：

```text
ω = k_heading · ψ_e + k_cross · e / (v + ε)
```

然后 clamp 到 `max_angular_vel`。

#### Pure Pursuit vs Stanley

| | Pure Pursuit | Stanley |
|---|---|---|
| 参考点 | 前方 lookahead 点 | 前轴 + 最近点 |
| 横向误差 | 隐式 | 显式 |
| 弯道 | 容易切内弯 | 更贴路径 |
| 调参 | `L` 为主 | `k`、速度相关 |
| 稳定性 | 较稳 | 高速可能振荡 |

Stanley 适合“想把横向误差压小”的场景；Pure Pursuit 更适合第一版。

### 4.4 L3：DWB-lite（采样 + critics）

#### 核心思想

在每个控制周期，采样多组 `(v, ω)`，向前模拟一小段轨迹，
给每条轨迹打分，选最好的那条，执行第一个控制量。

```text
for v in [v_min ... v_max]:
  for ω in [-ω_max ... ω_max]:
    traj = rollout(pose, v, ω, horizon)
    cost = w_path   * distance_to_global_path(traj)
         + w_goal   * distance_to_goal(traj)
         + w_obs    * obstacle_cost(traj, local_costmap)
         + w_heading* heading_error(traj)
         + w_vel    * |v - v_desired|
    keep best
apply best.first_command
```

#### 关键概念

| 概念 | 作用 |
|---|---|
| 采样空间 | `(v, ω)` 网格，或加速度空间 `(a, α)` |
| rollout | 用差速模型 `x += v cosθ dt`、`y += v sinθ dt`、`θ += ω dt` |
| horizon | 往前看多久（如 1.0~2.0 s） |
| critics | 每个评分项，权重决定行为 |
| local costmap | 障碍代价，DWB 必须看局部地图 |
| footprint | 机器人足迹，判断碰撞 |

#### 和官方 DWB 的关系

官方 `nav2_dwb_controller::DWBLocalPlanner` 就是：
**TrajectoryGenerator + 多个 Critic + GoalChecker**。
你自己写一个 5×7 采样的 DWB-lite，再读官方代码，会非常顺。

#### 为什么它是“局部规划器”

因为它显式评估“未来会撞哪、离路径多远、朝哪走”，
而不是只用当前误差做反馈。这是 PID/Pure Pursuit 没有的。

### 4.5 L4：MPPI-lite（采样 + 软最大）

#### 核心思想

MPPI = Model Predictive Path Integral，采样型模型预测控制。

和 DWB 的区别：

- DWB 在每个周期独立采样 `(v, ω)`，选一条；
- MPPI 维护一条**控制序列** `U = [u0, u1, ..., uN-1]`，
  每次在它周围加噪声采样 K 条序列，模拟未来，按代价做**加权平均**更新 `U`。

```text
初始化 U（全 0 或上一周期解）

每个控制周期:
  for k in 1..K:
    U_k = U + noise_k              # 高斯噪声
    traj_k = rollout(U_k)
    cost_k = trajectory_cost(traj_k)
  w_k = exp(-cost_k / λ) / Σ exp(-cost_j / λ)
  U = Σ w_k · U_k                  # 软最大加权
  apply U[0]
  U = shift(U)                     # 滚动时域
```

#### 关键参数

| 参数 | 作用 | 官方对应 |
|---|---|---|
| `batch_size` | 采样多少条轨迹 | `batch_size: 2000` |
| `time_steps` | 每条轨迹多少个控制步 | `time_steps: 56` |
| `model_dt` | 离散步长 | `model_dt: 0.05` |
| `vx_std`, `wz_std` | 噪声标准差 | 同名 |
| `temperature` | 软最大温度 λ | `temperature: 0.3` |
| `critics` | 代价项 | 官方 critics 列表 |

#### 为什么 MPPI 更“高级”

- 它在**控制序列空间**里优化，不是单步贪心；
- 软最大加权比“选一条最好的”更平滑；
- 能处理非凸代价、障碍、动力学约束；
- 但计算量大，参数多，调参难。

#### 学习建议

先写 DWB-lite，理解“采样 + 评分”；
再写 MPPI-lite，只把“选最好”换成“软最大加权”。
最后读官方 `nav2_mppi_controller`，重点看：

- `Optimizer` / `MPPIOptimizer` 的采样和更新；
- `critics/` 下每个 critic 的代价函数；
- `motion_model/` 下的差速/阿克曼模型；
- `noise_generator`。

### 4.6 L5：MPC-lite（梯度优化）

#### 核心思想

MPC = Model Predictive Control。和 MPPI 一样是滚动时域，但搜索方式不同：

- MPPI：随机采样很多控制序列，软最大加权；
- MPC：维护一条控制序列，用梯度/优化让它变好。

本项目实现一个可读的“梯度 MPC”：

```text
U = 上一周期解（或匀速直行）
for iter in 1..N:
  用有限差分算 cost 对每个 u[k] 的梯度
  U -= step * gradient
  投影到 [vmin,vmax] × [-wmax,wmax]
  如果 cost 没下降，step 减半（回溯线搜索）
执行 U[0]，滚动时域
```

代价：

```text
TrajectoryCost（path/goal/obstacle/heading/velocity/control）
+ terminal_weight · 终点距离
+ smoothness_weight · Σ|u[k]-u[k-1]|²
```

#### 参数

| 参数 | 作用 |
|---|---|
| `horizon_steps` | 预测步数 |
| `iterations` | 梯度迭代次数 |
| `gradient_step` | 梯度步长 |
| `line_search_steps` | 回溯次数 |
| `terminal_weight` | 末端代价 |
| `smoothness_weight` | 控制平滑 |

#### 和 MPPI 的区别

| | MPPI | MPC-lite |
|---|---|---|
| 搜索 | 随机采样 + 软最大 | 梯度 + 线搜索 |
| 计算量 | 随 batch 增大 | 随 iterations × horizon 增大 |
| 稳定性 | 噪声大时抖 | 可能局部极小 |
| 代表 | 官方 MPPI | 经典 MPC 教学版 |

## 5. PID vs 路径跟踪：到底差在哪

### 5.1 PID 是“反馈律”，不是“路径跟踪算法”

一个 PID 只回答：

> “当前误差是 e，我该输出多少控制量？”

它不回答：

- 参考点怎么选？
- 路径的切线方向是什么？
- 前方 1 米要转弯，现在要不要提前打角？
- 这个控制量在差速机器人上可实现吗？
- 前方有没有障碍？
- 速度/加速度/曲率是否超限？

所以 PID 通常作为**内环**：

```text
路径跟踪器（外环） → 期望速度/舵角 → PID（内环） → 电机
```

而不是整个控制器。

### 5.2 直接对 x、y 做 PID 为什么有问题

差速机器人只能控制：

```text
v：前进速度
ω：角速度
```

不能直接控制横向速度 `v_y`。如果你对 `x` 和 `y` 各做一个 PID，
得到的是世界坐标系下的“期望速度向量”，它可能指向机器人侧面。
你必须再把它转成 `v, ω`，而这一步又需要航向控制，问题并没有消失。

### 5.3 PID 在路径跟踪里的正确用法

| 用法 | 说明 |
|---|---|
| 速度环 PID | 让实际线速度跟踪期望线速度 |
| 舵角 PID | 阿克曼车的转向角控制 |
| 横向误差 PID | 作为 Stanley 的一项，或单独的 cross-track controller |
| 航向 PID | 让车头对准路径切线 |
| 纵向位置 PID | 沿路径的进度控制（较少单独用） |

也就是说：**PID 可以是控制器的一部分，但不是控制器的全部。**

### 5.4 六种方法对比

| 维度 | PID | Pure Pursuit | Stanley | DWB / MPPI | MPC |
|---|---|---|---|---|---|
| 本质 | 反馈律 | 几何跟踪 | 几何 + 横向误差 | 采样局部规划 | 梯度优化 |
| 参考点 | 需要你选 | lookahead 点 | 前轴最近点 | 多条候选轨迹 | 一条控制序列 |
| 非完整约束 | 需额外映射 | 天然满足 | 天然满足 | 显式建模 | 显式建模 |
| 前方弯道 | 无预见 | 有 lookahead | 部分 | 有 horizon | 有 horizon |
| 障碍物 | 不处理 | 不处理 | 不处理 | 处理 | 处理 |
| 速度/加速度限制 | 需外挂 | 部分 | 部分 | 显式 | 显式 |
| 调参难度 | 3 个增益 | 1 个 L | k、速度 | 多个 critic 权重 | 权重 + 步长/迭代 |
| 适合场景 | 低速简单轨迹 | 第一版路径跟踪 | 贴线要求高 | 真实局部避障 | 约束优化 |
| Nav2 对应 | 无 | RPP | 自定义 | DWB / MPPI | 无（核心外） |

### 5.5 一句话总结

> **PID 是“怎么纠偏”，Pure Pursuit 是“朝哪个点开”，
> DWB/MPPI 是“未来哪条路最安全、最舒服”，MPC 是“在约束下优化一条未来控制序列”。**
>
> 三者不是替代关系，而是不同层次。PID 可以作为内环，
> 但不能单独替代局部规划器。

## 6. 如何接入 Nav2

### 6.1 复用现有 A* 作为全局规划器

`params/controllers.yaml` 里保留：

```yaml
planner_server:
  ros__parameters:
    planner_plugins: ["GridBased"]
    GridBased:
      plugin: "nav2_astar_planner::AStarPlanner"
      allow_diagonal: true
      ...
```

只替换 `controller_server`：

```yaml
controller_server:
  ros__parameters:
    controller_frequency: 20.0
    controller_plugins: ["FollowPath"]

    FollowPath:
      plugin: "nav2_controller_lab::PurePursuitController"
      lookahead_distance: 0.6
      min_lookahead_distance: 0.3
      max_lookahead_distance: 1.2
      max_linear_velocity: 0.5
      max_angular_velocity: 1.9
      goal_tolerance: 0.25
```

### 6.2 插件四件套

`controller_plugins.xml`：

```xml
<library path="nav2_controller_lab">
  <class type="nav2_controller_lab::PurePursuitController"
         base_class_type="nav2_core::Controller">
    <description>Pure Pursuit 教学控制器</description>
  </class>
</library>
```

`package.xml`：

```xml
<export>
  <build_type>ament_cmake</build_type>
  <nav2_core plugin="${prefix}/controller_plugins.xml"/>
</export>
```

`CMakeLists.txt`：

```cmake
pluginlib_export_plugin_description_file(nav2_core controller_plugins.xml)
install(FILES controller_plugins.xml DESTINATION share/${PROJECT_NAME})
```

`.cpp`：

```cpp
#include "pluginlib/class_list_macros.hpp"

PLUGINLIB_EXPORT_CLASS(
  nav2_controller_lab::PurePursuitController, nav2_core::Controller)
```

### 6.3 坐标系处理

这是控制器最容易踩的坑：

```text
全局路径 frame_id = map
机器人 pose / 局部 costmap frame = odom
```

两种做法：

1. **在 `setPlan` / `computeVelocityCommands` 里用 TF 把整条路径变换到 `odom`**；
2. 或者把机器人位姿变换到 `map`，在 `map` 下计算，再把速度指令转回。

教学版建议做法 1，简单直接：

```cpp
geometry_msgs::msg::Path path_in_odom;
if (!tf_->transform(path, path_in_odom, costmap_ros_->getGlobalFrameID())) {
  throw nav2_core::ControllerTFError("路径变换失败");
}
```

注意 `costmap_ros_` 是**局部**代价地图，`getGlobalFrameID()` 通常是 `odom`。

### 6.4 目标检查

不要自己发明“到点”逻辑，优先用传入的 `goal_checker`：

```cpp
if (goal_checker->isGoalReached(
    pose.pose, path_.poses.back().pose, velocity))
{
  return zeroTwist();
}
```

这样 `xy_goal_tolerance` / `yaw_goal_tolerance` 由全局参数统一控制。

## 7. 测试与评价指标

### 7.1 纯控制核心的单元测试

把数学部分抽成不依赖 ROS 的函数：

```cpp
struct Control {double v; double omega;};

Control computePurePursuit(
  const Pose2D & robot,
  const std::vector<Pose2D> & path,
  double lookahead,
  double v_max);
```

测试用例：

| 用例 | 期望 |
|---|---|
| 直线路径，机器人无偏差 | `ω ≈ 0` |
| 直线路径，机器人偏左 | `ω` 指向右侧修正 |
| 圆弧路径 | `ω` 符号正确，大小有界 |
| 路径在身后 | 不输出反向大角速度，安全处理 |
| 空路径 | 返回 0 速度 |
| 到达目标 | 返回 0 速度 |
| 最大速度/角速度 | 输出被 clamp |

### 7.2 仿真集成指标

同一张地图、同一个起点/终点，比较：

| 指标 | 怎么取 |
|---|---|
| 到达时间 | `NavigateToPose` 总耗时 |
| 横向误差 RMSE | 机器人到全局路径的距离 |
| 航向误差 RMSE | 车头与路径切线夹角 |
| 最大角速度 | `/cmd_vel` |
| 最大加速度/急动度 | 对 `/cmd_vel` 差分 |
| 碰撞次数 | 局部 costmap 代价 / Gazebo 碰撞 |
| 路径长度 | 实际轨迹长度 |
| 重规划次数 | 日志 |
| CPU 占用 | `top` / `ros2 topic hz` |

### 7.3 推荐对比实验

```text
地图：tb3_sandbox
起点：(-2.0, -0.5)
终点：(1.5, 0.5)
全局规划器：A*（固定）
控制器：PID / Pure Pursuit / Stanley / DWB-lite / MPPI-lite
每个控制器跑 5 次，记录指标
```

> 固定全局规划器和地图，才能公平比较控制器。
> 不要一边换 A* 参数一边比较控制器。

## 8. 里程碑

### M1：Pure Pursuit 核心（不接 ROS）

- 输入：机器人位姿、路径、参数；
- 输出：`v, ω`；
- 用 gtest 测直线、偏移、圆弧、到达、空路径；
- 先不碰 TF、costmap、pluginlib。

### M2：Pure Pursuit 插件（接 Nav2）

- 实现 `nav2_core::Controller`；
- 处理 `map → odom` 变换；
- 配置 YAML，替换 `FollowPath`；
- 在 Gazebo 里完成一次导航。

### M3：Stanley

- 复用 M1 的测试框架；
- 对比 Pure Pursuit 的横向误差和弯道表现；
- 记录“为什么高速会振荡”。

### M4：DWB-lite

- 接入局部代价地图；
- 采样 `(v, ω)`，rollout，critics；
- 在动态障碍/窄通道里对比 Pure Pursuit。

### M5：MPPI-lite

- 维护控制序列；
- 采样 + 软最大加权；
- 对比 DWB 的平滑性、计算量、调参难度。

### M5.5：MPC-lite

- 维护控制序列；
- 有限差分梯度 + 投影 + 线搜索；
- 对比 MPPI 的平滑性、计算量、局部极小。

### M6：读官方实现

- `nav2_regulated_pure_pursuit_controller`
- `nav2_dwb_controller`
- `nav2_mppi_controller`
- 把官方 critics / motion model / noise generator 映射回自己的实现。

## 9. 建议先做哪一个？

> 仓库里已经提供了完整实现；这一节是“如果你要自己从零写”的建议顺序。
> 想直接跑实验，去看 [09 控制器实验手册](09_控制器实验手册.md)。

**先做 Pure Pursuit，不要先做 PID，也不要先做 MPPI。**

理由：

1. Pure Pursuit 足够简单，一天内能写出核心；
2. 它能真正让机器人沿路径走，给你正反馈；
3. 它是官方 RPP 的基础，学完能直接读生产代码；
4. 它会自然暴露“lookahead 太大切角、太小振荡”的问题，
   让你理解路径跟踪的核心矛盾；
5. 有了它，DWB/MPPI 的“多采样、多评分”才有对比对象。

PID 可以作为 L0 的对照实验，但不要把它当成第一版控制器。

## 10. 一页总结

```text
最简单的 controller：
  自己写 → Pure Pursuit
  官方用 → RegulatedPurePursuitController
  注意   → PID 不是完整路径跟踪器

推荐项目：
  src/nav2_controller_lab/
  复用 nav2_astar_planner 作为全局规划器
  控制器阶梯：PID → Pure Pursuit → Stanley → DWB-lite → MPPI-lite → MPC-lite

PID 的问题：
  只回答“怎么纠偏”
  不回答“参考点在哪、前方弯道、障碍、运动学约束”
  PID 可以作为内环或 Stanley 的一项
  不能单独替代局部规划器

控制器接入：
  继承 nav2_core::Controller
  实现 configure / setPlan / computeVelocityCommands / setSpeedLimit
  处理 map → odom 的 TF
  四件套注册
```
