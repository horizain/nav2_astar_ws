## 1. 先看懂链路：一次导航到底经过哪些环节

跑端到端之前，先把整条数据流画出来。后面每个坑都挂在这张图的某个点上。

```text
                        ┌──────────────── 仿真侧（gz sim，无头运行）────────────────┐
                        │  DiffDrive 插件                                          │
   ROS 侧               │   ├─ 发布 gz /odom、gz /tf（odom→base_footprint）          │
   controller_server ───┼─→ /cmd_vel(Twist) ──→ parameter_bridge(ROS_TO_GZ) ──→ ↑   │
        ↑               │   └─ /scan  ←─ 激光传感器（headless 下由服务端渲染，~5Hz）│
        │               └──────────────────────────────────────────────────────┘
 velocity_smoother ←── /cmd_vel_smoothed ←── collision_monitor（安全过滤）
        ↑                                             ↑
 /cmd_vel_nav(TwistStamped)          ↑             /cmd_vel_smoothed
        ↑                            │
 nav2_controller（FollowPath 动作）    │
        ↑                            │
 bt_navigator（行为树）── 规划 ──→ planner_server → AStarPlanner（我们的 A*）
        ↑                            │
        └──────── NavigateToPose ────┘（你的测试脚本/ RViz 按钮 发的目标）

 TF 两段（各自独立，断哪段都不行）：
   map → odom          由 AMCL 发布（要先给它初始位姿！）
   odom → base_footprint 由 gz DiffDrive 发布、parameter_bridge 桥到 ROS /tf
   base_footprint → ... → base_link 等   由 robot_state_publisher 发在 /tf_static
```

速度指令链条（值得背下来，排错时逐环抓话题）：

```text
controller_server ─→ /cmd_vel_nav ─→ velocity_smoother ─→ /cmd_vel_smoothed
                  ─→ collision_monitor ─→ /cmd_vel ─→ gz 桥 ─→ 轮子
```

**实测数据流速**（本机 WSL2、headless、`RTF≈1.0`，用 rclpy 计数 6 秒）：

| 话题 | 频率 | 说明 |
|---|---|---|
| `/odom` | ~28 Hz | DiffDrive `odom_publish_frequency=30` |
| `/tf` | ~41 Hz | odom→base_footprint |
| `/scan` | **~5 Hz** | headless 下服务端渲染激光，明显低于 SDF 标称值 |

记住 `/scan` 只有 5Hz —— 坑 3 的所有连锁反应都从它开始。

## 2. 坑一：初始位姿"看起来发了，其实没发"

### 2.1 现象

无头跑 nav2，AMCL 每 2 秒一条警告：

```text
[amcl]: AMCL cannot publish a pose or update the transform. Please set the initial pose...
```

`tf2_echo map odom` 永远超时。而 `odom → base_footprint` 是通的（doc 14 怀疑的
"TF 断链"其实不存在——那是残留进程干扰，见 [03 §6.3](03_教学进度记录.md)）。

### 2.2 排查（有弯路，弯路本身有价值）

AMCL 收到初始位姿时第一行日志就是 `initialPoseReceived`（`amcl_node.cpp:537`）。
日志里**一条都没有** → 消息根本没到 AMCL。三种途径逐一试：

1. `ros2 topic pub --once /initialpose ... --ros-args -p use_sim_time:=true`

   **失败，而且失败得很隐蔽**：`ros2 topic pub` 自己有个 `-p/--print` 选项，
   命令行里的 `-p` 被它吃掉，报 `argument -p/--print: invalid int value` ——
   但因为我们只 `tail -2` 看输出，把用法报错错看成了"发布成功"。
   **命令压根没执行，我们却以为发过了。**

2. `ros2 service call /reinitialize_localization nav2_msgs/srv/SetInitialPose ...`

   两个问题：消息嵌套少一层（`PoseWithCovarianceStamped.pose.pose.position`，
   少一层报 `object has no attribute 'position'`）；修好后 CLI 的 service call
   **挂起 100+ 秒无响应**（本机 CLI 与 DDS 发现配合不稳定）。

3. 换成 rclpy 单进程直调 service —— 也超时（`wait_for_service(8s)` 失败），
   但**话题发布兜底成功**：连发 5 次 `/initialpose`，AMCL 立刻接受，
   `map → odom` 出现。

### 2.3 根因

不是 QoS（AMCL 用 `SystemDefaultsQoS`，与 pub 默认参数完全匹配），而是
**CLI 工具在本机环境不可靠**：参数解析陷阱 + DDS 发现/daemon 缓慢。
`activate_nodes.py` 早就验证过同一结论——批量生命周期调用必须绕开 CLI。

### 2.4 修复（`e2e_nav_test.py` 里的实现）

```python
# 优先：service 直调（请求-应答，无 QoS 匹配歧义）
r = self.call_service(SetInitialPose, '/reinitialize_localization',
                      SetInitialPose.Request(pose=msg), timeout=8.0)
if r is not None:
    return True

# 兜底：话题连发 5 次，每次间隔 0.5s（--once 可能丢，多发不会）
pub = self.create_publisher(PoseWithCovarianceStamped, '/initialpose', qos)
for _ in range(5):
    pub.publish(msg)
    rclpy.spin_once(self, timeout_sec=0.5)
```

初始位姿的值**必须与 Gazebo 出生点一致**（本文场景 = `(-2.0, -0.5, 0°)`），
原因见 [03 §6.4 坑三](03_教学进度记录.md)——这是 nav2 最经典的坑，这里不再复述。

### 2.5 教训

1. **"没有报错"不等于"执行成功"**。截取输出要看到明确的成功标志
   （AMCL 的 `initialPoseReceived` 日志、`map→odom` TF 出现）才算数。
2. 自动化链路里**优先用 service/action（请求-应答）**，话题发布做兜底且多发送几次。
3. `ros2 topic pub` 的 `-p` 是它自己的 `--print`；透传节点参数要用
   `--ros-args` 且位置有讲究——干脆别在自动化里用 CLI 发布。

## 3. 坑二：use_sim_time 诊断脚本的"瞬间退出"陷阱

### 3.1 现象

写了个探针节点订阅 `/odom`、`/scan`、`/amcl_pose` 想统计频率，结果
**全部为 0**，连确定在发的 `/odom` 都收不到。一度怀疑 DDS 共享内存残留、
QoS 不匹配……都排除了。同样的订阅逻辑内联在另一个脚本里却
**一切正常**（odom 168 条/6s）。

### 3.2 根因（一个 if 条件的教训）

两个脚本唯一的区别是探测窗口的计时方式：

```python
self.set_parameters([Parameter('use_sim_time', ..., True)])   # 节点用仿真时间
start = self.get_clock().now()          # ← 陷阱在这里
while (self.get_clock().now() - start).nanoseconds < 10e9:    # "跑 10 秒"
    rclpy.spin_once(self, timeout_sec=0.2)
```

`use_sim_time=True` 的节点，**在收到第一帧 `/clock` 之前 `now()` 返回 0**。
循环第一轮 `spin_once` 收到 `/clock`，`now()` 直接跳到仿真时刻（比如 75s），
`75e9 > 10e9` → 窗口条件立刻不满足 → 循环退出。
**所谓"统计 10 秒"实际只跑了一次 0.2 秒的 spin**，订阅还没完成发现，
自然一条消息都收不到。

### 3.3 修复

```python
# 先等第一帧 /clock，再取 start（或者干脆用 time.time() 墙钟计时）
while rclpy.ok():
    rclpy.spin_once(self, timeout_sec=0.5)
    if self.get_clock().now().nanoseconds > 0:
        break
start = self.get_clock().now()
```

### 3.4 教训

1. **`use_sim_time` 节点的 `now()` 在首帧 `/clock` 前是 0**——任何
   "以 now() 计时的循环"都要先确认时钟已经活过来。
2. 排障时"换个写法就正常"的对照组本身就是最重要的证据：
   先做差异对比（这题里只差 3 行），再怀疑基础设施。

## 4. 坑三：进度检查器误杀慢速导航（最耗时间的一个）

### 4.1 现象

初始位姿 OK、全链路 TF OK、目标已发、机器人在动——但每隔 10 秒：

```text
[controller_server]: [ERROR] Failed to make progress
[controller_server]: [WARN]  [follow_path] [ActionServer] Aborting handle.
[behavior_server]:  [WARN]  Collision Ahead - Exiting Spin
[behavior_server]:  [WARN]  spin failed
[planner_server]:   [WARN]  A* 规划完成 ……（重规划又来一轮）
```

180 秒超时，机器人只走出 1.8m；MPPI 那次更典型：**距离目标最近只剩 0.43m**，
然后被重规划"甩"去绕远路，永远不收敛。

### 4.2 排查：把"每 10 秒一次"当线索

`Failed to make progress` 来自 `SimpleProgressChecker`：**10 秒内位移不足
`required_movement_radius`(0.5m) 就判失败**。为什么机器人会慢到 10 秒走不
0.5 米？逐层测量：

1. **控制环频率**：日志反复出现
   `Control loop missed its desired rate of 20.0 Hz. Current loop rate is 5.5~8.3 Hz`。
2. **为什么慢**：读 `controller_server.cpp:524-532`——每个控制周期要等
   局部代价地图"新鲜"（`isCurrent()`，最多等 `costmap_update_timeout`=0.3s）。
   局部代价地图由 `/scan` 驱动，而 headless 下 `/scan` 只有 ~5Hz
   （WSL2 服务端渲染瓶颈，第 1 节实测）→ 控制环被拖到 ~6Hz。
3. **为什么爬**：MPPI-lite（100 采样、15 步 rollout）在膨胀场里要给
   "撞障碍"的轨迹打高分，输出速度被压到 0.03~0.3 m/s——这是采样类控制器的
   **正常谨慎行为**，不是故障。
4. **连锁反应**：慢速爬行 → 进度检查判失败 → FollowPath abort → BT 触发恢复
   （旋转，又因为贴着障碍 "Collision Ahead" 失败）→ 强制重规划 → 路径突变 →
   机器人朝新路径走 → 又被判"无进度"……**系统在正确的组件之间形成了一个
   错误的循环**。

### 4.3 根因

官方默认 `required_movement_radius: 0.5 / movement_time_allowance: 10`
是给 **20Hz 控制环 + 0.26m/s 巡航速度**的环境设计的。在本机
（headless 渲染 5Hz 扫描 → 6Hz 控制环 → 采样控制器谨慎爬行）下，
这个阈值把"慢而正常"误判为"卡死"。

### 4.4 修复（`nav2_params_controller_lab.yaml`）

```yaml
progress_checker:
  plugin: "nav2_controller::SimpleProgressChecker"
  # 教学实验室专用调参（2026-11 端到端实验结论）：
  # 本机 WSL2 headless 下激光只有 ~5Hz，costmap 更新把控制环拖到 ~6Hz，
  # 采样类控制器（DWB/MPPI/MPC）在障碍附近会以 0.03~0.3 m/s 谨慎爬行。
  # 官方默认（0.5m/10s）会把这种"慢而正常"的移动误判为失败，
  # 触发 abort -> 恢复行为 -> 重规划 的搅局循环，机器人永远到不了目标。
  # 放宽为 0.15m/25s：允许慢速绕障，只拦截真正的卡死。
  required_movement_radius: 0.15
  movement_time_allowance: 25.0
```

**为什么不是无限放宽**：0.15m/25s 仍然能拦住真卡死（比如坑住不动、原地打转），
只是给慢速绕障留了合法生存空间。阈值的意义是区分"慢"和"死"，不是消灭"慢"。

### 4.5 教训

1. **周期性报错 = 定时器**。`每 10 秒一次`直接指向 `movement_time_allowance: 10`，
   这条线索让排查少走一半弯路。
2. 性能问题要**逐层测频率**：传感器 → costmap → 控制环，断点在哪一层，
   根因就在哪一层。
3. 恢复行为（recovery）是双刃剑：环境不适配时，"规划→失败→恢复→重规划"
   自己会构成死循环。观察 BT 在干什么和观察控制器在干什么同样重要。

## 5. 坑四：终点朝向死锁（最有价值的一个 bug）

### 5.1 现象

MPPI 顺畅地绕过圆柱阵，**停在了距目标 0.25~0.40m 处一动不动**，
feedback 的 `剩余 0.25~0.40 m` 恒定，直到超时。没有报错、没有 abort、
没有恢复行为——系统"健康地"卡死了。

### 5.2 排查：三个"谁"对不上了

1. **目标检查器查什么**？读 `simple_goal_checker.cpp:103-118`：
   `SimpleGoalChecker::isGoalReached` **先查 xy（容差 0.25m），再查 yaw**
   （容差 0.25rad ≈ 14°）。状态机 `stateful=True`：xy 满足后就只查 yaw。
2. **和谁比**？`controller_server.cpp:635`：
   `end_pose_ = path.poses.back()`——**路径最后一个位姿**，
   也就是 A* 写入的目标位姿（`astar_planner.cpp`：路径末位姿朝向 = 目标朝向 ✓）。
3. **控制器在终点做什么**？读 `mppi_core.cpp:43`：

   ```cpp
   if (remainingDistance(robot, path) <= params_.goal_tolerance) {
       return result;   // 直接返回默认零指令 —— 机器人停车，完。
   }
   ```

   六种控制器核心都只负责"**跟路径**"：路径走完就输出零速。
   **没有任何一段代码负责"原地旋转到目标朝向"**。

   死锁闭环：位置进了容差 → xy 通过 → 只剩 yaw 不对 → 控制器停车不转 →
   yaw 永远不满足 → 导航永不返回成功。

### 5.3 为什么官方控制器没有这个问题

官方 RPP 有独立的 `rotateToGoalHeading` 阶段；官方 MPPI 有 `GoalAngleCritic`
在终点区对准目标朝向。**"终点旋转"是控制器插件契约里隐含的最后一棒**，
我们的教学版控制器全部漏掉了这一棒。

### 5.4 修复：基类统一补上"终点旋转阶段"

**设计决策：放在 `ControllerBase`（适配层），而不是改六个 core。**
理由：这是六种控制器共享的"最后一棒"职责，和 TF 变换、限速一样属于适配层；
纯算法抽到 `path_utils`（无 ROS 依赖，可单测）——延续本项目的分层原则
（"算法层不碰 ROS，适配层不碰算法细节"）。

**① 纯算法 `path_utils::rotateInPlace`**（`path_utils.hpp/.cpp`）：

```cpp
Control rotateInPlace(const Pose2D & robot, double goal_yaw, double max_angular_velocity)
{
  Control command;
  command.linear = 0.0;
  // P 控制：误差越大转得越快。符号约定 —— 目标朝向在逆时针方向（正误差）
  // 时输出正 w，机器人左转（ROS 坐标系 z 轴朝上）。误差收敛到 0 时指令
  // 自然归零，不会振荡。clamp 同时把误差限定在 [-π, π] 的最短方向上。
  const double yaw_error = normalizeAngle(goal_yaw - robot.yaw);
  command.angular = clamp(2.0 * yaw_error, -max_angular_velocity, max_angular_velocity);
  return command;
}
```

**② 基类接线**（`controller_base.cpp` 的 `computeVelocityCommands`）：

```cpp
if (!path.empty() && remainingDistance(robot, path) <= goal_tolerance_) {
  // 终点旋转阶段：位置已到，转向目标朝向。跳过控制器核心
  // （它们会在终点输出零速），也跳过代价地图锁（不查障碍）。
  command = rotateInPlace(robot, path_terminal_yaw_, terminal_angular_velocity_);
} else if (needsCostmap()) {
  ...
}
```

**③ 一个容易踩的细节：终点朝向不能用 `path.back().yaw`**。
`transformPlanToLocalFrame()` 里有一句：

```cpp
// 统一用相邻点切线，避免上游朝向缺失或不一致
recomputePathYaw(path);
```

它把所有 yaw **覆盖成相邻点切线**——A* 写在末位姿里的目标朝向会被冲掉。
所以必须在覆盖之前单独保存：

```cpp
// 保存原始路径末位姿的朝向（AStarPlanner 已写入目标朝向），供终点旋转
// 阶段使用。注意：recomputePathYaw 会把所有 yaw 覆盖成相邻点切线，
// 所以必须在这之后、覆盖之前提取 —— 这正是"路径终点朝向"和
// "路径切线"是两回事的地方。
path_terminal_yaw_ = path.back().yaw;
recomputePathYaw(path);
```

**④ 新参数**：`terminal_angular_velocity`（默认 1.5 rad/s），
每个控制器实例可独立覆盖。

**⑤ 已知局限（诚实声明）**：终点旋转阶段**不查局部代价地图**。如果目标
贴着障碍，原地旋转可能扫到障碍物。footprint 碰撞检查本来就是 doc 14
"后续可做"清单里的一项，这里先欠着。

### 5.5 配套：目标容差的两处调整

只补终点旋转还不够——实测 MPPI-lite 在目标"口袋区"（圆柱阵东侧）的
收敛点在 **0.27m** 处，0.25m 的 xy 容差永远差 2cm 够不着。两处联动调整：

```yaml
general_goal_checker:
  xy_goal_tolerance: 0.35   # 0.25 → 0.35，差速小车教学场景合理精度
  yaw_goal_tolerance: 0.25
# 六个控制器实例统一：
goal_tolerance: 0.40        # 0.25 → 0.40
```

**顺序约束（注释里写了，这里再强调）**：`goal_checker.xy(0.35)` 必须
**小于** 控制器的 `goal_tolerance(0.40)` —— 终点旋转阶段要先于检查窗口介入，
机器人才会先对准朝向，检查器才有机会在 xy 窗口内判成功。
反过来配（checker 更大）会出现"xy 已判过（stateful 锁存）、机器人还在远处
乱转"的怪状态。

### 5.6 验证：5 个新单测 + 端到端 PASS

### 5.7 教训

1. **"健康地卡死"比"报错地崩溃"更难查**——没有异常可抓，只能对账：
   检查器要什么、控制器给什么、中间谁该补位。
2. **接口契约有隐含条款**。`nav2_core::Controller` 的文档没写"你要负责终点
   旋转"，但 goal checker 会查 yaw——契约的另一半在**使用方的行为**里，
   读官方插件的对应实现（RPP/MPPI）是发现隐含条款的最快路径。
3. **"终点朝向"和"路径切线"是两回事**。路径后处理（切线重算、平滑、
   插值）都可能冲掉语义信息；凡是要"保留语义"的数据，要么在覆盖前提取，
   要么让覆盖函数带豁免参数。

## 6. 三个控制器的端到端表现（教学案例）

同一张地图（tb3_sandbox：9 个半径 0.15m 圆柱按 1.1m 间距摆成 3×3 阵，
外围六边形墙）、同一条 A* 路径、同一目标 (1.5, 0.5, 90°)。

### 6.1 Pure Pursuit：楔死（无避障的必然结局）

**轨迹**：从出生点 (-2, -0.5) 直线东行 1.79m，卡死在 (-0.21, -0.36)。

**几何账**：A* 路径从圆柱缝隙穿过（缝隙宽 1.1-0.3=0.8m，缝隙中线距两侧
圆柱心各 0.55m）。Pure Pursuit 的前视点（0.6m）在弯道处会**切弯**，
实际轨迹向弯内侧偏移。卡死点距圆柱 (0,0) 圆心 0.41m，距柱面 0.26m，
机器人半径 0.22m——**物理间隙只剩 4cm**，加上定位/控制噪声直接顶上。

**日志指纹**：`Failed to make progress`（顶住不动）+ 恢复旋转
`Collision Ahead - Exiting Spin`（costmap 确认周围真有障碍）。

**定位系统是清白的**：卡死时 gz 真值 (spawn+odom) 与 AMCL 估计仅差 0.02m。

> **教学要点**：几何控制器（PID/PP/Stanley）**没有障碍物的概念**，
> 它们的世界只有一条路径。只要全局路径从窄缝穿过、控制器有切弯倾向、
> 环境有物理障碍——三者齐备就是必死局。这正是"为什么需要 DWB/MPPI/MPC"
> 的最直观答案。改进方向（不在本文实施）：A* 输出更宽的走廊
> （提高 inflation 对代价的影响）或给几何控制器加"贴路径误差大就减速"。

### 6.2 MPPI-lite：成功（采样 + 软最大加权敢走"贵但可行"的缝）

**轨迹**（节选，完整见 `docs/results/logs/e2e_mppi_success.log`）：

```text
(-2.00, -0.50) 出发 → 东行穿缝 (-1.45,-0.52) → (-0.57,-0.53)
→ (-0.27,-0.52) → (0.63,-0.55) → (1.78,-0.63) 北转
→ (1.81,-0.09) → (1.79,0.28) 剩余0.40m → 终点旋转 → ✅ SUCCEEDED
```

**为什么它能过而 PP 不能**：MPPI 每周期采样 100 条带噪声的控制序列，
按"路径贴合 + 障碍代价 + 前进收益"软最大加权。缝隙里的代价虽高但
**前进收益更大**，加权平均后它选择"贵但可行"的走廊，以 0.03~0.3 m/s
谨慎爬行通过——**慢，但方向正确**（这也是坑 3 要放宽进度检查的原因）。

**代价**：全程 ~46s（直线距离 3.64m，平均 ~0.08m/s），且在目标口袋区
出现过 0.27m 的收敛僵持（坑 5.5 调容差的由来）。

### 6.3 DWB-lite：冻结（最小代价选择的结构性弱点）

**现象**：走了 0.19m 后完全静止，恢复行为挪动后再次静止，
`obstacle_weight` 从 100 降到 10 也无法解冻，直到超时。

**机理分析**（`trajectory_cost.cpp::evaluateTrajectory`）：
DWB-lite 对每条采样轨迹求**总代价最小**：

```text
cost = 1.0·路径贴合 + 2.0·(轨迹末端→路径终点距离) + 100·(障碍均值)
     + 0.5·航向 + 0.2·|v-0.5| + 0.05·|w|
```

冻结点周围是膨胀场（圆柱+墙的真实代价，实测局部代价地图在机器人周围
0.5~1.0m 处布满 INSCRIBED 级代价）。**v=0 轨迹**恰好停在代价 0 的格子上：
路径贴合≈0、障碍≈0，只付 |0-0.5|×0.2=0.1 的速度罚；而任何前进轨迹都要
**穿过整片膨胀区**，障碍均值代价轻松上到两位数，压倒 goal_weight 的前进
收益（2.0×0.75m≈1.5）。**原地不动永远是最小代价解 → 冻结。**

把 obstacle_weight 降到 10 只是把"压倒"变成"仍然压倒"（前进收益 1.5 vs
障碍代价 ~6），解不了结构性问题。

> **教学要点**：
> 1. DWB 的"总代价最小"和 MPPI 的"软最大加权"在**局部最优**面前行为
>    截然不同：前者会停在最好的坏选择上，后者会被采样噪声推着离开。
>    这不是 bug，是两类评分器的**结构差异**——也是真实世界 DWB 需要
>    `EscapeTrajectory` 类恢复机制的原因。
> 2. **代价地图是对的，被冤枉过一次**：排障时我们一度把膨胀场当"幽灵
>    障碍"（见 `docs/results/logs/e2e_dwb_frozen.log` 排查期），后来对着
>    真实几何逐格核算才确认 costmap 无辜。**先算几何再怀疑数据**。
> 3. 他们自己的单测 `ChoosesForwardOnClearStraightPath` 测的是"空旷直路
>    会前进"——膨胀场里的冻结正好落在测试盲区。评分器改动必须配
>    "窄缝/膨胀场"类测试用例。

**遗留**：DWB-lite 在窄缝世界的冻结是已知开放项，改进思路见第 9 节。

> **2026-11 更新：DWB 已解冻并通过端到端验证**（同任务 10 秒到达，
> 比 MPPI 快 4.6 倍）。冻结的完整数学解剖（逐点手算 + 相变表 +
> 模型预测 x=-1.80 与实车 x=-1.81 的厘米级对齐）与修复推导见
> **[16 局部轨迹评分函数设计](16_局部轨迹评分函数设计.md)**。

## 9. 教训汇总

1. **自动化里别信 CLI 的"成功"**：`ros2 topic pub --once` 可能因参数解析
   根本没执行；成功要以**对端的确认日志**为准（AMCL 的
   `initialPoseReceived`、TF 出现）。
2. **service/action 优先，话题兜底多发**：请求-应答没有 QoS 匹配歧义。
3. **use_sim_time 节点的 `now()` 在首帧 /clock 前是 0**：计时循环先等时钟。
4. **周期性报错 = 某个定时器在到期**：把报错间隔和参数里的时间常量对账。
5. **慢 ≠ 死**：进度检查的阈值要匹配本环境的真实速度分布
   （传感器频率 → costmap → 控制环，逐层测）。
6. **恢复行为会构成死循环**：abort → recovery → replan → abort，
   观察行为树和观察控制器同样重要。
7. **接口契约的隐含条款藏在使用方里**：goal checker 查 yaw，
   所以 controller 插件必须负责终点旋转——读官方插件的对应实现。
8. **路径后处理会冲掉语义**：切线重算覆盖了目标朝向；要保留的信息
   在覆盖前提取（或让覆盖函数带豁免）。
9. **排障先算几何再怀疑数据**：我们把正确的膨胀场误判成"幽灵障碍"，
   用真实障碍位置逐格核算才翻案。
10. **min-cost 评分器会停在"最好的坏选择"上**（DWB 冻结），
    采样+加权（MPPI）天然更抗局部最优——两类算法的结构差异，
    在参数怎么调都救不了的时候，要怀疑结构。
