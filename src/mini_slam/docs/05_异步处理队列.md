# 05 异步处理队列：回调只入队，处理在工作线程

对应 slam_toolbox 的 async 模式（相对 sync 模式逐帧同步处理）。

## 动机

建图一帧的成本不是常数（闭环触发时 SPA + 建场要几十毫秒）。同步处理时，
回调耗时直接反压到订阅队列：高倍速回放、高频激光、或闭环风暴帧，
订阅队列堆积 → 丢的是**最新帧**（DDS 队列先进先出）→ 定位/建图用旧数据。

## 设计（节点层，核心保持同步）

```
scan_callback:  转换点云 + 查 odom → 入队（限长 queue_size=10）
                溢出：丢最旧 + 计数告警
worker 线程:    条件变量等待 → 取帧 → process_one（按模式分发）→ 更新 TF
析构:           stopping_=true → notify → join
```

关键取舍：
- **队列限长 + 丢最旧**：宁可丢帧也不能让处理积压（积压会让定位用旧扫描，
  比"暂时少一帧"危害大）。丢弃计数周期性告警。
- **核心保持同步**：Mapper 不感知线程——异步是节点的调度策略，不是算法的。
  这与 slam_toolbox 的 async_slam_toolbox_node 一致。

## 验证

bag 2 倍速回放（处理压力 ×2）：**14 次闭环、0 丢帧**——worker 完全跟上。
队列压小到 5 也没有触发溢出，说明单帧处理延迟 < 输入间隔。

## 踩坑（P7，重量级）

验证时曾出现"节点全程零处理"，一度怀疑队列实现。真凶是
**过期的 ros2 CLI daemon**：daemon 跨进程常驻，缓存着僵尸时代的
DDS 发现状态；新节点（bag play / rclpy）启动后互相发现不了，
`ros2 topic hz`、数据流全部静默失败。

```bash
ros2 daemon stop && ros2 daemon start   # 或直接 kill daemon 进程
```

排查口诀：**"收不到数据"先分三层**——① 数据源在不在发（裸 hz）？
② daemon 缓存是不是旧的？③ 订阅方 QoS 兼容吗？本次是 ②。
