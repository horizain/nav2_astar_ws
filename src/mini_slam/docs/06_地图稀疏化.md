# 06 地图稀疏化：长时运行的内存控制

对应 slam_toolbox 的地图生命周期管理（长期运行时移除冗余扫描）。

## 问题

每个节点持有整帧扫描点云（TB3 一帧 ≈ 360 点）。长时运行 1 万帧 =
~60MB 点云 + 建场成本随帧数增长。而其中大量扫描是**冗余的**：
往返运动时，同一段路被扫了十几遍。

## 设计：图结构永久保留，点云按覆盖关系剪枝

关键不变量：**保留点永不释放**。

```
sparsify()（每 sparsify_every 个节点跑一次；节点默认 50）：
  从最老节点到保底窗口（最近 sparsify_min_keep_recent 帧永不剪枝；
  节点默认 50），贪心铺点：与"上一个保留点"距离 ≥ sparsify_keep_radius
  （节点默认 0.8m）才保留；落在保留点覆盖半径内的中间扫描 → 释放点云
  （保留空壳与位姿）。下面验证数字来自 test_sparsify 的测试配置
  （keep_radius=1.5m / min_keep_recent=10 / every=25）。
```

为什么这样是可靠的：释放的扫描被"保留点"等价覆盖（半径内），
而保留点永不释放——覆盖关系不会因后续剪枝而断裂。

释放的收益（`test_sparsify` 实测）：
- 内存：点云压缩到基线的 36%
- 匹配场构建更快：场只由存活扫描组成
- 地图渲染：被剪枝区域由存活扫描等价覆盖（占据格保留约 82%）

保留的用途：位姿与边仍在图里（闭环、SPA、轨迹可视化不受影响）；
存活扫描覆盖整条轨迹（定位、渲染不受影响）。

渲染侧的失效：`set_scan()` 会递增 `PoseGraph::pose_revision()`，因此
稀疏化释放点云后，增量地图渲染器下一次 `update()` 会走全量重建路径，
不会把已释放的历史射线结果继续当作有效内容。

## 验证（test_sparsify.cpp）

往返 15m × 4 段（116 节点，重访密集）：
- 点云 20474 → 7422（36%）
- 节点数不变（116 → 116，图结构完整）
- 地图占据格 907 → 746（保留约 82%，等价覆盖）

## 踩坑

- 最初版本用"被最近窗口覆盖就释放"，往返场景下远端没有新扫描覆盖，
  压缩率只有 55%——改成"沿轨迹贪心铺点"才把保留集合变成 O(路径/半径)。
- `last_kept` 声明成了 Vec2 却赋值 Pose2——SE2 位姿带朝向，
  铺点时的朝向判断（后续可扩展）需要完整位姿。
