# 08 交互式建图：在 RViz 里拖拽位姿图节点

对应 slam_toolbox 的 **interactive SLAM**：建图过程中发现某段轨迹被拉歪（长走廊
里的假闭环、单帧匹配滑移），不用重建整张图——在 RViz 里把那个节点拖到它应该在
的位置，后端以该节点为硬约束重跑一次 SPA，地图随之重建。

slam_toolbox 是用自研的 RViz panel（`SlamToolboxPlugin`）实现的。本仓库**不写
自定义 Qt/RViz 插件**，而是用 ROS 标准的 `interactive_markers`
（`visualization_msgs/InteractiveMarker`）——任何 RViz 都能显示、拖拽，节点侧只
需要 `interactive_markers::InteractiveMarkerServer`。

```
RViz InteractiveMarkers display
        │  拖动（POSE_UPDATE，只更新客户端显示）
        │  松手（MOUSE_UP）
        ▼
/mini_slam/feedback  ──► marker_feedback()  ──► Mapper::move_vertex(id, pose)
                                                     │  graph.pose(id) = pose
                                                     │  bump_pose_revision()
                                                     │  SpaSolver::solve(graph, id)   ← 节点 0 与 id 同时固定
                                                     │  rebuild_index()
                                                     ▼
                                             stats_.solves++ → 地图缓存失效
/mini_slam/update    ◄── marker timer（0.5s）重建 marker + 地图重渲染
```

## RViz 操作步骤

1. 启动（默认关闭，必须显式打开）：

   ```bash
   ros2 launch mini_slam mini_slam_online.launch.py \
       enable_interactive_markers:=true
   ```

   节点日志会打印 `交互式 marker 已启用：RViz 加 InteractiveMarkers display，
   Update Topic=/mini_slam/update（最多显示 N 个节点）`。

2. RViz 里 **Add → By display type → InteractiveMarkers**（RViz2 里在
   `rviz_default_plugins`，名字就是 `InteractiveMarkers`）。

3. 把该 display 的 **Update Topic** 设成 `/mini_slam/update`（默认值是
   `/basic_controls/update`，不改收不到任何东西）。

4. 此时每个位姿图节点显示为：半透明蓝色球（XY 平面拖动）+ 半透明橙色圆盘
   （绕 z 旋转）。拖动后松手即提交。

5. 松手后节点会短暂回到后端给出的位姿：被拖节点保持你放下的位置，它的**邻居
   节点**按边观测让步（闭环边/里程计边都会拉），地图与 marker 在 0.5s 内刷新。

交互式 marker 的 3 个接口（由库约定，全部挂在本节点命名空间下）：

| 名称 | 类型 | 方向 |
|---|---|---|
| `/mini_slam/update` | `visualization_msgs/InteractiveMarkerUpdate` | 节点 → RViz |
| `/mini_slam/feedback` | `visualization_msgs/InteractiveMarkerFeedback` | RViz → 节点 |
| `/mini_slam/get_interactive_markers` | `visualization_msgs/srv/GetInteractiveMarkers` | 服务（RViz 初次连接拉全量） |

## 参数

| 参数 | 默认 | 运行时可改 | 说明 |
|---|---|---|---|
| `enable_interactive_markers` | `false` | ❌ | 启动期决定是否创建 `InteractiveMarkerServer`；运行期修改明确拒绝（`运行时不支持修改，请通过 launch 参数重启节点`） |
| `interactive_marker_max_vertices` | `200` | ✅（必须 ≥ 1） | 最多显示多少个节点；超过后均匀抽样，改动在下一个 marker timer 周期生效 |

**为什么默认关闭**：`InteractiveMarkerServer` 会额外建一个发布器、一个订阅器和
一个服务，并让 RViz 侧持续渲染 marker。默认建图流程不需要它们，所以默认关掉
（`ros2 topic list | grep mini_slam` 在关闭时为空；打开后才有
`/mini_slam/update`、`/mini_slam/feedback`）。

**抽样规则**（`interactive_marker_max_vertices = N`，图有 `M > N` 个节点）：

- `stride = ceil(M / N)`，从 0 开始每隔 stride 取一个 → 覆盖整条轨迹，而不是
  只显示最后 N 个。老闭环节点常常正是需要手动纠正的那一个，必须能被拖到。
- 再补上最后一个节点（抽样点可能跳过 `M-1`）。
- 因此实际显示数 ≤ N + 1。想拖某个没被显示的老节点：临时调大
  `interactive_marker_max_vertices`，或先保存图。

## 语义（重要）

- **固定两个节点**：`node 0` 永远固定（消除位姿图整体平移/旋转的规范自由度），
  被拖节点 `id` 也固定（`SpaSolver::solve(graph, fixed_id)`）。节点 0 是建图
  起点；拖它没有意义，它的位姿不会因为拖拽而改变——除非你拖的就是它，此时它
  仍是固定点，等于"整体地图不许动，只有邻居让步"。
- **残差压力给邻居**：被拖节点与邻居之间的边观测不再成立，代价函数里会留下
  残差；SPA 让**其它节点**动来尽量满足边。这就是"用户说这里是对的"的语义。
  极端情况下（拖动幅度远超匹配窗口）那一圈会明显变形——这是交互式纠偏的固有
  代价，slam_toolbox 同样如此。
- **只在 mapping 模式生效**：localization 模式图是冻结的（地图由 map_server
  提供），节点不显示可拖拽 marker；即使手动发 feedback 也会被拒绝并 WARN。
- **只在 MOUSE_UP 提交**：拖动过程中的 `POSE_UPDATE` 事件不跑 SPA（否则一次
  拖动会触发上百次图优化），只由 marker server 更新客户端位姿。
- **失败兜底**：节点 id 越界 / 位姿含 NaN·inf / 反馈帧不是 `map_frame` →
  拒绝并 `WARN_THROTTLE`，图与统计完全不变。
- **地图刷新**：`stats_.solves++` 让 `MapRenderKey` 失效（地图重渲染）；
  `pose_revision++` 让 `IncrementalMapBuilder` 走全量重建（不是增量）——
  被拖节点的历史扫描位置全变了，增量射线更新在这里是错的。

## 线程与锁

marker timer（0.5s）与 feedback 回调、map timer、TF timer、worker 线程并发：

- marker timer：`mapper_mutex_` 内只做快照（mode / 顶点数 / nodes / solves /
  pose_revision / max_vertices / frame + 选中节点位姿），**释放锁后**才
  `clear()/insert()/applyChanges()`。
- feedback 回调：`mapper_mutex_` 内调 `move_vertex()`（含一次 SPA），释放后
  才 `setPose()/applyChanges()`。
- 锁顺序真实形态（复核结论，无环）：`InteractiveMarkerServer::processFeedback`
  是**持着自己的递归锁**（`std::recursive_mutex`）分发给我们的回调的，所以
  feedback 路径是 `server.mutex_ → mapper_mutex_`；marker timer 路径是
  `mapper_mutex_`（只做快照）→ 释放 → `server.mutex_`。timer **从不**在持有
  `mapper_mutex_` 时去碰 server，因此不存在
  `mapper_mutex_ → server.mutex_ → mapper_mutex_` 的环。递归锁还保证了在
  feedback 回调里再调 `setPose()` 不会自锁。
- `interactive_marker_max_vertices_` 由 `mapper_mutex_` 保护（参数回调写、
  marker timer 读）。
- 代价：一次 SPA 期间 feedback 回调持着 server 锁，marker timer 的重建会被
  推迟到下个周期——这是有意的（宁可延后刷新，也不在回调里放锁让图半改）。

## 限制（诚实记录）

- **不做完整 slam_toolbox 式拖拽 UI**：没有节点编号显示、没有"拖动整段子图"、
  没有撤销栈/历史、没有交互式闭环确认（slam_toolbox 的
  `interactive_slam` 还带 loop closure 的手动 approve）。这里只有"移动单个
  节点 + 局部重优化"，是**教学级**的交互编辑。
- **不含交互式重定位**：拖完不会重新插值历史扫描，只把已有节点的扫描按新位姿
  重画；拖歪了只能再拖回来，没有 undo。
- **稀疏化后的节点拖拽意义有限**：点云已被释放（`sparsify_enabled`）的老节点
  拖过去不会长出新的地图内容，只能纠正位姿（地图由存活扫描覆盖）。
- 一次拖动 = 一次全图 SPA。节点数上千时会有明显停顿（同步在 feedback 回调里
  跑，期间 worker 与地图 timer 等锁）；大规模图请用
  `interactive_marker_max_vertices` 限制显示数、或离线编辑。

## 踩坑

- **MOVE_PLANE 的平面法线是控制帧的 x 轴**，不是 z 轴。RViz
  （`rviz_default_plugins/.../interactive_marker_control.cpp` 的
  `intersectSomeYzPlane` 与 `movePlane`）用
  `control_frame_orientation * control_orientation.xAxis()` 当平面法线。
  所以想让节点在 map 的 XY 平面里拖，控制朝向必须绕 y 转 -90°（把 x 轴转到
  世界 +z）；照抄"orientation.w = 1"会得到一面竖直的拖动平面，鼠标一动节点就往
  z 方向跑（2D 场景里表现为拖不动）。
- 控制帧被转 90° 后，控制里的可视化 marker 也会跟着转：球无所谓，圆盘得反向
  补偿 90° 才是水平的。
- **ROTATE_AXIS 的转轴同样是控制帧 x 轴**，用同一个朝向即可获得"绕世界 z"的
  yaw 旋转。
- **feedback 的客户端互斥**：`InteractiveMarkerServer` 对同一个 marker 1s 内
  只接受同一个 `client_id` 的反馈（防两个 RViz 抢同一个节点）。自动化测试发
  feedback 时要用固定 `client_id`，否则第二条会被静默丢弃。
- 只处理 `MOUSE_UP`：RViz 的拖动过程会以 30~60Hz 发 `POSE_UPDATE`，在回调里
  跑 SPA 会把节点拖成幻灯片。
- marker timer 的 key 必须含 `stats_.solves`：只比顶点数的话，拖动后顶点数没变，
  marker/地图都不会刷新（这正是 Phase 4B 地图缓存踩过的同一个坑）。
